整体看，这份任务清单质量很高，已经具备交给 AI Agent 分批执行的基础。它最好的地方是把产品方向、原型评审、视觉实现、交互实现、学习体验和 AI 协作拆开了，并且明确了不能动业务底座的边界。

但我不建议现在就原样交给 Agent 开始执行。

问题不在于拆得不够细，而在于：部分依赖关系不够严谨、若干验收标准还不可测、个别任务超出了当前约束，而且六周工作量可能被低估。

我会给它一个评价：

# 8/10

任务拆解成熟度

距离真正可执行，还需要一轮「工程化校准」。

## 一、最需要修改的 8 个问题

### 1. 六周计划与 25 个任务的工作量不匹配

这是我认为最重要的问题。

按照你之前确定的节奏，每周约 10 小时，六周总计 60 小时。

但这份清单包含：

- 三页桌面端 + 移动端高保真原型。
- 三套图谱背景、节点视觉、关系线和动效。
- 搜索、节点详情、路径探索等交互。
- 首页、知识详情、文档阅读空间改造。
- 学习舱改造。
- AI 上下文协作。
- 多页面移动端适配。
- 全量测试、性能验收和文档整理。

这不是简单的六周 UI 改造，而是一个涉及设计、前端工程、交互和回归测试的综合项目。

尤其是 T08–T14，图谱视觉和交互本身就可能占用大量时间。

建议：把六周定义为六个阶段，而不是承诺六周完成全部 25 项任务。

每个阶段完成后根据验收结果决定是否进入下一阶段。可以保留原任务编号，但不要让 Agent 把六周理解成硬性工期。

### 2. T01 的性能基线还不够严谨

你已经注意到了 20,000 节点 / 3.4 FPS 与 8,000 节点实测之间的矛盾，这是正确的。

但「以 8,000 节点实测为准」还不够。

性能基线至少需要记录：

| 项目     | 应记录内容                    |
| -------- | ----------------------------- |
| 测试数据 | 节点数、关系边数、数据来源    |
| 测试环境 | 浏览器、设备、分辨率          |
| 测试条件 | 是否启用标签、搜索、动效      |
| 性能结果 | FPS、初始化耗时、交互响应时间 |
| 测试方法 | 预热时间、测量时长、重复次数  |

特别要注意：8,000 个节点不等于 8,000 个节点加上任意数量的关系边。

建议增加一个明确要求：

T01 只负责核对历史数据和建立测试方法，不改图谱实现；后续 T24 使用相同数据、相同设备和相同测试条件进行回归比较。

另外，20k / 3.4 FPS 应该标注为历史记录，不能直接作为当前项目的性能结论。

### 3. T02 和 A7 存在关键的设计语义冲突

你已经发现了这个问题，但我建议不要把它留到后面。

目前清单涉及四种概念：

- 探索状态：蓝色。
- AI 状态：紫色。
- 掌握证据：青色。
- 待复习状态：橙色。

但原项目已经存在记忆档位的琥珀色表达。

这里必须把三个维度彻底分开：

| 维度       | 表达什么                         | 建议视觉方式 |
| ---------- | -------------------------------- | ------------ |
| 记忆新鲜度 | 这个知识点多久没有被有效回顾     | 节点亮度     |
| 复习状态   | 是否到了应该复习的时间           | 橙色提示标记 |
| 掌握证据   | 是否有足够的学习行为支持掌握判断 | 青色外环     |

另外，选中状态应该属于交互状态，而不是知识本身的业务状态。

这样就不会出现「一个知识点既是待复习，又是掌握状态，但只能显示一种颜色」的问题。

建议：在 T02 增加一张状态语义表，并在 T09 明确规定视觉编码的优先级。

### 4. T05 的六种交互状态与 T12–T14 的关系需要明确

T05 要求六种状态全部有对应画面：

1. 自由探索。
2. 搜索聚焦。
3. 节点选中。
4. 路径探索。
5. 学习模式。
6. AI 探索。

而 T12、T13、T14 又分别实现其中的交互能力。

这里容易产生一个问题：原型阶段已经设计了一套状态逻辑，工程实现时又由 Agent 自己重新设计一遍。

建议在 T05 的交付物中，除了六张状态画面，再增加：

六状态交互状态转换图。

例如：

自由探索

搜索聚焦

输入关键词

节点选中

点击节点

路径探索

选择两个节点

AI 探索

从节点唤起 AI

学习模式

从图谱进入学习舱

仅为状态关系示意，实际转换规则应在 T05 评审时确认。

这样 T12–T14 实现时就有明确依据，而不是自由发挥。

### 5. T13 的「九个入口」描述不准确

当前写的是：

> 名称、文档、标签、摘要、记忆状态、关联节点、最近学习、阅读 / 回忆 / 询问 AI 九个入口。

前七项其实是信息展示，后三项才是操作入口。

建议改成：

- **信息区域：**名称、所属文档、标签、摘要、记忆状态、关联节点、最近学习记录。
- **操作区域：**阅读、主动回忆、询问 AI。
- **辅助操作：**编辑、查看完整关系等，是否保留取决于现有能力。

这会直接影响面板的视觉层级。

我还建议将「九个入口」改成「三项主要操作 + 辅助信息」，避免 Agent 把所有内容都做成按钮。

### 6. T12 的搜索范围可能超出现有搜索能力

T12 写了：

> 标题 / 正文 / 标签 / 关系 / 学习状态检索。

但同时要求复用现有搜索索引、不改变原搜索行为。

这里存在潜在冲突。

例如，现有搜索可能只支持标题、正文、标签，而关系和学习状态可能没有进入搜索索引。

如果要求 Agent 一次性实现所有检索维度，就可能间接改变 API、数据库查询或搜索行为，违反总约束。

建议在 T01 增加：

现有搜索能力矩阵：

| 检索维度 | 当前是否支持 | 实现方式                           |
| -------- | ------------ | ---------------------------------- |
| 标题     | 待核实       | 复用现有能力                       |
| 正文     | 待核实       | 复用现有能力                       |
| 标签     | 待核实       | 复用现有能力                       |
| 关系     | 待核实       | 若无现成能力，不新增后端逻辑       |
| 学习状态 | 待核实       | 若无现成能力，作为前端筛选而非搜索 |

这样才能真正做到不改变搜索行为。

### 7. T21 的 AI 功能需要进一步收紧

T21 包含：

- 解释知识点。
- 查找关联。
- 解释关系。
- 生成回忆问题。
- 检查结构缺口。

前四项比较容易对应现有 AI 工具。

最后一项「检查结构缺口」需要特别小心。

现有的 `search_knowledge`、`read_segment`、`propose_actions` 并不自动意味着系统具有可靠的知识缺口检测能力。

我建议将它定义为：

AI 候选缺口分析：

- 只根据已检索到的知识内容提出候选。
- 明确区分事实、推测和建议。
- 不自动创建知识点或关系。
- 用户确认后才进入现有预览—确认—应用流程。

否则很容易让 AI 把「没有检索到关联」误判成「这个知识点确实缺少关联」。

### 8. T24 的验收标准存在不够稳定的问题

现在要求：

> E2E 6/6；现有测试全绿。

我建议区分两件事：

- **既有自动化测试：**所有当前测试通过。
- **核心业务 E2E：**明确列出六条关键业务链路并逐条通过。

六条链路可以考虑：

1. 首页进入图谱。
2. 搜索并定位节点。
3. 查看节点详情。
4. 从节点进入主动回忆。
5. 提交复习并返回图谱。
6. 从节点唤起 AI 并完成安全操作流程。

这样即使以后 E2E 测试数量从 6 条变成 10 条，也不会让验收标准失效。

另外，`npm run typecheck`、`lint`、`test`、`build`、`test:e2e` 必须先核实 `package.json` 中是否真实存在这些脚本，不要把命令名称当成项目既有事实。

## 三、还有一个容易被忽视的问题：视觉系统的范围太大

B 组目前包含：

- 3 套背景。
- 4 种节点状态。
- 4 种关系线。
- 4 种动画模式。
- 3 个独立主题维度。

组合起来已经相当复杂。

例如，三套背景 × 四种关系线 × 四种动画模式，就有 48 种组合，还没有算节点状态。

这会带来大量视觉调试工作。

我建议第一轮控制为：

| 模块     | 第一轮建议                                 |
| -------- | ------------------------------------------ |
| 背景     | 3 套，可切换                               |
| 节点     | 4 种状态                                   |
| 关系线   | 2 种：普通、强调                           |
| 动效     | 2 种：静态、轻量动态                       |
| 主题偏好 | 背景独立切换，节点和关系线先使用统一默认值 |

后续用户真的需要更丰富的自定义，再扩展关系线和动效。

尤其是你的图谱已有性能压力，不要为了视觉丰富而把图谱变成一个持续消耗资源的动态背景。
