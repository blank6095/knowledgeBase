## 一、先确定产品主线：从“管理知识”转向“掌握知识”

你目前的产品容易出现一种情况：知识点越来越多，图谱越来越漂亮，AI 能力越来越强，但打开应用之后，依然不知道今天该学什么、学完之后是否真正记住了。

建议把核心体验收敛为一个闭环：

1. 今天学什么

从现有知识中挑出少量值得复习的内容，给出推荐原因。

2. 不看笔记，先回忆

回答问题，再查看参考答案和原始知识来源。

3. 记录实际掌握情况

记录答题表现、错题与来源查看情况，而不只是记录阅读时长。

4. 下次复习更有针对性

结合复习历史和现有记忆度，重新安排下一次学习。

这是一条待验证的产品主线，不代表它已经被证明最适合你。我们先让它服务于你自己的 Java、React、AI Agent 等学习内容，再根据真实使用体验调整。

### 这个闭环要遵守三个原则

1. 减少决策成本：打开首页后，尽量一步就能开始学习。
2. 以主动回忆为核心：阅读和图谱浏览是辅助，不把它们当作掌握知识的证据。
3. 先记录事实，再做智能推荐：先收集真实答题结果，再考虑更复杂的记忆算法。

尤其要注意：你现有的 \\(M=\\exp(-\\Delta t/S)\\)是基于时间和稳定度计算的记忆度指标，不等于实际掌握程度。应该保留它，但不要直接把它当作答题成绩或知识掌握率。

细化今日学习页面方案

第一版只需要三种推荐来源：

* 错题优先：之前答错或无法回答的知识。
* 到期复习：已有复习记录且到达下一次建议复习时间的知识。
* 继续学习：没有复习记录时，从最近阅读或未读知识中选择。

注意：这三类的排序规则应该简单、可解释。不要一开始就做一个复杂的 AI 排序系统。

技术实现步骤

1. 复用现有知识查询、记忆度计算和阅读历史，不重建一套数据模型。
2. 新增一个服务端 `<span>getTodayLearningItems()</span>`（名称可按现有项目规范调整），统一返回推荐知识及 `<span>reason</span>`。
3. 首页用服务端组件加载数据，交互部分再使用客户端组件。
4. 没有待复习内容时展示“开始学习”或“选择知识”，不要出现空白页面。
5. 点击任一项目，直接进入对应的自测或知识详情，不再要求用户二次搜索。

验收标准

* 首屏可以看到今日推荐内容和推荐原因。
* 从首页到开始一次复习，最多 2 次点击。
* 空知识库、没有到期复习、推荐知识被删除等情况均有合理降级。
* 推荐结果不会把已删除或无效的知识引用出来。
* 个人使用时，生成推荐不需要调用 LLM；避免无意义的费用和等待。

### P0：最小主动回忆 / 自测功能

这是本轮最值得投入的功能。它直接决定项目能不能从知识整理工具变成学习工具。

第一版不需要完整考试系统，也不需要题库管理。只实现一个最小学习单元：

示例题

Java · 集合框架

问题：HashMap 在发生哈希冲突时，主要通过什么机制处理？

查看参考答案

上面是交互示意，不是已接入数据库的项目功能。

第一版需要的能力：

1. 从一个知识点生成一道问题，或使用已有内容构造问题。
2. 用户先回答，之后才能查看参考答案。
3. 展示答案来源，并能返回原知识点。
4. 用户记录“答对 / 部分掌握 / 没答出”。
5. 保存复习记录，以便之后重新推荐。

建议优先支持短文本问答。选择题、填空题、计时考试和复杂评分先不做。

技术实现步骤

* 先检查现有知识段的数据结构和 AI 调用层，确定问题生成可以使用的最小上下文。
* 将生成题目、参考答案、来源知识 ID、必要的内容版本信息定义为结构化结果。
* 服务端校验生成结果，确保引用的知识确实存在、答案不为空、来源能定位。
* 前端按“问题 → 输入答案 → 查看参考答案 → 记录结果”的状态机实现，不允许默认直接展示答案。
* 复用已有 DeepSeek 调用层和缓存机制。生成失败时，允许重新生成或改为直接阅读原知识，不阻断整次学习。
* 题目和答案由 AI 生成，不意味着内容一定正确。答案应能追溯到原文；无法可靠生成时，提示用户查看原文，而不是伪造来源。

验收标准

* 从一个有效知识点开始，到完成一次自测、记录结果、返回来源，整个流程可走通。
* 页面刷新后，已经提交的复习结果仍然存在。
* 用户未提交结果时，不会误记为已掌握。
* 无效的知识 ID、生成失败、空答案、重复提交均有明确处理。
* 每条复习记录都能追溯到知识点和当次问题；若原文之后发生变化，不应把旧答案悄悄当成最新答案。
* 至少覆盖成功流程、LLM 失败、无效来源、重复提交和数据库写入失败的测试。

### P0：复习记录与掌握情况

这一部分不建议直接重做现有记忆度系统，而是新增一条与阅读记录并行的复习记录链路。

阅读记录回答的是：“我看过这份知识多久？”

复习记录回答的是：“我在某个时间点，能不能回忆起这份知识？”

这两个问题都重要，但不能混为一谈。

#### 建议的数据结构

先按下面的逻辑设计，再对照现有 Drizzle Schema 确认哪些字段已经存在，避免重复建表。


| 字段                         | 用途                                                                     |
| ---------------------------- | ------------------------------------------------------------------------ |
| `<span>id</span>`            | 复习记录ID                                                               |
| `<span>knowledgeId</span>`   | 对应的知识点ID                                                           |
| `<span>question</span>`      | 本次使用的问题                                                           |
| `<span>answer</span>`        | 用户提交的回答                                                           |
| `<span>result</span>`        | `<span>correct</span>`、`<span>partial</span>`、`<span>incorrect</span>` |
| `<span>sourceVersion</span>` | 问题生成时所依据的知识内容版本                                           |
| `<span>reviewedAt</span>`    | 实际复习时间                                                             |
| `<span>nextReviewAt</span>`  | 建议的下一次复习时间，可为空                                             |

有两个实现细节需要特别注意：

* 如果用户回答可能涉及个人学习内容，建议仅存完成复习所必需的数据，并避免额外记录原始 Prompt 或学习画像原文，遵循项目已有的数据约束。
* `<span>nextReviewAt</span>`应是复习调度信息，不是记忆度 \\(M\\)。记忆度继续按照项目既有原则读取时计算，不要将动态指标持久化。

第一版调度规则不要复杂化。

例如，可以先试用以下规则，之后根据真实学习效果调整：


| 本次结果 | 下一次复习建议 |
| -------- | -------------- |
| 没答出   | 1天后          |
| 部分掌握 | 3天后          |
| 答对     | 7天后          |

这些时间只是初始实验参数，不是已经验证的最优间隔。当天可以允许用户主动再次练习，但不要因为连续点了多次“答对”就快速拉长间隔。

验收标准

* 复习记录和阅读记录相互独立，原有记忆度计算不回归。
* 用户可以查看最近复习的知识、结果和原始来源。
* 同一个知识点多次复习时，每次都有独立记录。
* 删除知识点、编辑原文、重复提交等边界行为符合现有项目的数据一致性约定。
* 所有涉及多表写入的操作，按项目既有事务约定执行。

## 三、P1：让推荐逐渐变聪明，而不是一开始就上复杂算法

当上述最小闭环运行起来后，再让系统依据复习结果安排学习顺序。

### 推荐规则：先确定性排序，后考虑智能化

建议第一版采用一个容易解释的排序规则：

1. 优先展示之前答错的知识。
2. 其次展示已到期、尚未复习的知识。
3. 再展示最近学过但还没有任何自测记录的知识。
4. 最后补充未读或用户主动选择的知识。

如果同一类别里有很多条，再结合距离上次复习的时间、现有记忆度和用户手动选择排序。

不要在第一版就把这些因素揉成一个难以解释的综合分数。先让你看得懂推荐为什么出现，之后才有条件判断排序是否有效。

### 技术实现步骤

* 把复习记录、现有阅读记录和记忆度计算结果汇总到服务端推荐函数。
* 为每条推荐输出 `<span>reason</span>`，例如“上次未答出”“复习已到期”。
* 首页只消费统一的推荐结果，不在多个前端组件里各写一份推荐规则。
* 通过固定时间和固定测试数据验证排序，避免测试结果受 `<span>Date.now()</span>`影响。
* 等积累到一定量的真实记录后，再评估是否需要修改稳定度或复习间隔。

### 验收标准

* 推荐顺序符合明确规则，结果可重复验证。
* 每条推荐都能解释原因。
* 没有复习历史时仍能正常推荐。
* 不因为新增复习功能而让原来的记忆度、图谱或知识详情页出现不一致。
* 对推荐函数建立 Vitest 单元测试，至少覆盖错题优先、到期复习、无历史数据和重复知识去重。

## 四、P1：验证你是否真的学得更好了

你现在的主要用户就是自己，因此没必要先做完整的数据分析平台。但建议增加一个非常轻量的学习反馈区域，帮助你判断产品有没有价值。

可以先展示四项数据：

* 本周完成了多少次主动回忆。
* 本周有多少道题没答出或只部分掌握。
* 之前答错的知识，在后续复习中表现如何。
* 连续几天真正完成了学习，而不是仅仅打开过网站。

这些指标要区分清楚：打开网站、阅读知识、完成自测、后续答对，是不同层次的行为。

建议把“后续复习表现”作为更有意义的观察指标，但不要在样本很少时宣称长期记忆已经改善。短期答对只能说明当前表现，不能证明长期保留效果。

### 验收标准

* 每周汇总可以由现有复习记录和阅读记录计算得出，不需要额外重复存储派生指标。
* 无数据时显示明确的空状态，而不是显示 0% 掌握率。
* 不把阅读时长、图谱节点亮度或 AI 生成题目数量直接解释为学习成果。
* 你能在一周结束时回答三个问题：我实际练了多少？哪些知识最薄弱？哪些知识在再次复习时有改善？

## 六、哪些现有功能应该暂缓

这里最关键的是：暂缓不等于删除，也不等于现有功能做得不好，而是它们暂时不是解决当前瓶颈的最高杠杆。


| 功能                                   | 本轮决策 | 原因与重新启动条件                                                                                                                         |
| -------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 知识图谱视口裁剪、社区聚合、WebGL/WASM | 暂缓     | 项目假设约8,000个节点以上才考虑更重的规模化方案。先用现有压测夹具测出真实瓶颈，再决定是否优化。project-context(1).md                       |

| pgvector与更复杂的RAG检索              | 暂缓     | 先用现有关键词检索和知识检索验证自测质量。只有检索经常找不到正确来源，且关键词方案难以解决时，才考虑向量检索。                             |

| 多用户、注册、团队协作                 | 暂缓     | 项目明确定位为单用户个人知识库，没有必要为当前目标引入用户体系和权限复杂度。project-context(1).md                                          |
| 全面UI重构                             | 暂缓     | 只调整首页、答题页和结果反馈中影响学习启动与完成的体验问题，不做全站换肤。                                                                 |

## 八、最终验收：什么情况下才算这轮迭代成功？

我建议把验收拆成三层，而不是仅以“功能开发完成”为标准。

第一层：工程可用

首页推荐、自测、来源回看、结果持久化和下一次复习均能正常运行；关键异常有测试覆盖；原有知识导入、图谱、阅读记录与 Agent 不发生回归。

第二层：学习闭环成立

你可以从首页直接开始学习，完成主动回忆，查看可信的知识来源，保存结果，并在后续时间看到相应的复习推荐。

第三层：个人学习价值成立

14 天内出现真实、重复的学习行为；推荐和自测没有持续增加负担；部分曾经答错的知识在后续复习中表现改善。若使用频率没有改善，应先修正产品流程，而不是继续扩充功能。

这些标准中，工程和流程是否跑通可以明确验收；使用频率、题目质量和后续表现则属于实验结果，不应该预先保证。
